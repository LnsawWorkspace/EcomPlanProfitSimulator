## 1. 心智模型

```
当前工作区库（库名 = 工作区 UUID）
├── planMetas   方案（keyPath=id）            ← 参数的主体，一对一
├── planParams  方案参数（keyPath = 方案的 id）  ← ★本文件主角★ 与方案"兄弟"关系
└── ...
```

- **一个方案（planMeta）对应一条参数记录（planParams）**：`planParams.id` 直接复用方案的 `id`（源码注释："复用 PlanMeta 的 ID，这样就不用搞什么外键"），一对一。
- **参数页是独立页面**：`/page/planParams/planParams.html`，必须带 URL 参数 `?workspaceId=&groupId=&planId=` 才能加载（三者缺一 → 页面隐藏，显示「方案不存在，或已被移除。」）。
- **删除方案不级联删参数**（planMetas 的坑 3）：删方案后参数记录成孤儿。`plan_meta_ops.js params` 命令可审计孤儿。
- **填参数 ≠ 建方案**：方案（名称/描述）在工作台建；参数（售价/单量/退款/商品/赠品/费用/广告）在参数页填。

### 业务语义：7 个模块 & 目标 vs 商品信息（重要，先理解再填）

> 参数页有 **7 个 params-card 模块**（按页面顺序）：`目标` / `推广` / `商品信息` / `赠品信息` / `每单支出` / `部分订单支出` / `固定支出`。
> 对应到 8 个模型：目标=Sale+Refund、推广=Advertising、商品信息=Goods、赠品信息=Gift、每单支出=ExpensePerOrder、部分订单支出=ExpenseMNPerOrder、固定支出=ExpenseFixed。

**「目标」模块的售价/单量，是【这一个方案 / 这一个单品】的整体数字：**
- 一个方案 = 一条逻辑渠道（见 `planMetas.md`），对应一个上架链接里的**一个规格（SKU 组合）**。
- 例：上架一个链接，里面添加了一个规格——这个规格卖「内裤」，内裤一共 4 条不同颜色/样式。此时：
  - **售价** = 这个规格（这条内裤链接）**卖多少钱**（1 个价，整个方案一个售价）。
  - **商品信息模块** = 这个规格下的 **4 条商品记录**（每条 = 一个颜色/样式 SKU），比如「粉色」是 2 件，那么商品信息里这一行就是 **粉色 / 件数 2**。

**关键层级（不要绕晕）：**
```
方案（一个逻辑渠道 / 一个链接规格）
├── 目标：售价（1 个） / 目标单量（1 个）   ← 整个方案的售价与总销量目标
└── 商品信息：N 行 SKU                       ← 该规格下的颜色/款式明细，每行可多件
    例：内裤规格 = 4 行（黑/白/粉/蓝），粉色 2 件 → 粉色行 件数=2
```
- **商品可以建多条**（4 个颜色 = 4 行），**每条商品的件数也可以 >1**（粉色 2 件 = 件数 2）。
- **单品的件数总和 ≠ 目标单量**：商品信息的件数是"这个规格下实际铺货的 SKU 明细"，目标单量是"整个方案要卖多少单"，两者含义不同、无需相等。
- **改售价只影响「目标」**：商品行的含税/不含税成本是各自的成本，和售价无关；售价是顾客付的钱，成本是商品行自己的钱。

### 业务语义：三个支出模块（每单 / 部分订单 / 固定，重要）

> 三个模块怎么区分：**按"哪些订单会产生这笔支出"** 来归类。

| 模块 | 含义 | 典型例子 | 与退款的关系 |
|------|------|---------|-------------|
| **每单支出**（ExpensePerOrder） | **每个订单都会支出**的费用 | 类目服务费、技术服务费、运费、包装费、运费险（如开通）、其他按单必出的项目 | 有回收率列（用目标模块退款 × 回收率计损） |
| **部分订单支出**（ExpenseMNPerOrder） | **只有部分订单才有**的支出 | 手续费（信用卡/花呗等支付渠道费）；给部分买家发几元补贴/安抚金；部分订单的小额退款/部分金额退款；其他各种"仅部分订单"的近似的支出项目 | **退款率与回收率都在行内单独填**（独立于目标模块，因为只作用于部分订单） |
| **固定支出**（ExpenseFixed） | **固定金额，是多少就是多少** | 一次性/周期性的固定花费（人力提成等） | **不涉及退款**（无退款、无回收率列） |

**记忆要点**：
- **每单支出**：100 单就 ×100——"每单必出"（运费险这类按单算的）。
- **部分订单支出**：先有"订单比例"（`orderPer`，0-1）说明覆盖多少比例的订单，再算金额；手续费、补贴、小额退款都归这里。
- **固定支出**：总额固定，不随单量/退款变化；填多少就是多少，别按单乘。

**支出成本的单位跟着成本类型走（重要，三个支出模块通用）**：
- 每个支出行都有「成本类型」（`valueType`，UI 单选 `cost_type_money` 固定金额 / `cost_type_percent` 百分比）。
- **固定金额（num）**：支出成本填**金额**，如 `135.38` = 135.38 元（存 `valueMoney`）。
- **百分比（per）**：支出成本**直接填百分数值**——想写 0.6% 就填 `0.6`，站点内部自动 ÷100 存成 0.006（`valuePercentage`，0-1 小数）。填 `135.38` 即 135.38% = 0.13538。**同一个数，单位随类型变**——金额 135.38 元 ≠ 百分比 135.38%（≈0.13538）。
- 所以填支出时先确认成本类型再填数：**百分比行直接写百分数（0.6 = 0.6%），不要写 0.006**；也别把"135.38 元"填进百分比行（那会变成 135.38% 的比例）——反之亦然。

**「基于」（来源字段 / 来源类型）——选百分比时必须选（重要，三个支出模块通用）**：
- HTML 官方说明（第 816 行）：「当类型是"百分比"时，**必须选择**」——选了百分比（per）就必须设置「来源字段」+「来源类型」，否则不完整。
- **来源字段（`base`）**：百分比基于什么的百分比。目前选项只有 `-`（未选）和 `售价`（JS 里 `options = ["-", "售价"]`，暂时只支持售价），**存值就是字符串 `'售价'`**。
- **来源类型（`baseHaveTax`，布尔）**：基于**含税售价** 还是 **不含税售价**（UI：`#xxx-with_tax` 含税默认 / `#xxx-no_tax` 不含税）：
  - **基于含税售价**：逻辑上相当于基于**目标模块里的售价字段**（你填的那个售价，含税口径）。
  - **基于不含税售价**：实际上是基于**换算后的收入**（含税售价 ÷ (1+税率) 得到的不含税金额）。
- **含税/不含税关系**（换算口径）：不含税 = 含税 / (1 + 税率)；含税 = 不含税 × (1 + 税率)。「基于不含税」时站点会先把售价换算成不含税收入再取百分比。
- **固定支出（ExpenseFixed）特殊**：它**也有「来源字段」**（`#expenseFixed-base`），选百分比时需要选 base；但**没有「来源类型」（含税/不含税）控件**——即固定支出选百分比时**不需要区分含税还是不含税**（站点当前未实现该控件，将来是否实现待定）。

### 业务语义：赠品——视同销售 vs 销售费用（税务，重要）

> 赠品信息模块每行有「费用类型」列（`#gift-deemedSale` 视同销售=是 / `#gift-salesExpense` 销售费用=否，默认**销售费用**）；模型存 `subjectType`，取值就是中文字符串 `'视同销售'` / `'销售费用'`（默认 `'销售费用'`）。

**税务规则（判断选哪一种）**：
- **通常赠品都是「视同销售」**：税法规定，买一送一（买内裤送内裤、买袜子送袜子）这类"送 XXX"都要**视同销售、额外缴税**——注意是**额外缴税**，会直接影响利润，所以大多数赠品必须选「视同销售」。
- **少数特殊情况可以用「销售费用」**：备用的低价值配件，如**买空调送空调出风口滤网**（滤网价值必须很低）。
- **反例（不宜做费用）**：空气净化器送滤网做成费用就不太合适——滤网对净化器而言价值不算低，属于实质赠品，应视同销售。
- **判断原则**：先按税法判断是否"赠品（送 XXX）"→ 是则视同销售；只有明确属于低价值备用配件类才考虑销售费用。

**视同销售时的税额计算（HTML 第 676 行官方说明）**：
- 「当视同销售时候，**若公允价值大于 0，则使用公允价值计算税额**」——视同销售模式下，公允价值是计税额的依据。
- 所以选「视同销售」的赠品行，公允价值要如实填（且**不含税**，税法口径，与商品一致）。

**⚠️ 强制使用「销售费用」时的提醒义务（AI 操作必须遵守）**：
- 当**用户强制要求**把本应视同销售的赠品做成「销售费用」时，AI **必须先提醒、后执行**：
  1. **提醒税法规定**：按税法，买一送一这类"送 XXX"的赠品应视同销售并额外缴税；
  2. **提供规定链接**：附上相关税法依据（如《增值税暂行条例实施细则》第四条"将自产、委托加工或者购进的货物无偿赠送其他单位或者个人"视同销售等条款，可检索国家税务总局法规库 https://www.chinatax.gov.cn 相关条款）；
  3. **说明后果**：将赠品按费用处理而不视同销售，可能被税务机关认定为**偷税漏税**，面临补税、罚款、滞纳金等风险；
  4. **提醒之后，按用户的需求执行**——不因提醒而拒绝操作，尊重用户最终决定。

### 业务语义：销售金额分摊（成本法 vs 公允法，重要）

> 目标模块的「分摊方式」选择（`#sale_method_cost` 成本分摊法 / `#sale_method_fair` 公允分摊法，默认**成本分摊法**）。

**它是用来解决什么问题的**：
- 当**商品信息模块里出现多个商品，且它们的销项税率不一致**时，需要决定"售价（GMV）怎么分摊到各商品头上"——这就是销售金额分摊的用途。
- 只有一个商品、或所有商品销项税率一致时，分摊方式不影响结果，默认成本法即可。

**两种方式的规则**：
| 方式 | 选择器 | 规则 |
|------|--------|------|
| 成本分摊法（默认） | `#sale_method_cost` | 按各商品的**成本**比例分摊售价；**不需要填公允价值，填 0 即可**（公允值在成本法下不参与计算，无意义） |
| 公允分摊法 | `#sale_method_fair` | 按各商品的**公允价值**比例分摊售价；**商品信息里每一条都必须填写公允价值**，漏填会出错 |

**⚠️ 公允价值是不含税的（税法规定）**：
- `fairValue` 存的是**不含税**公允价值（成本/售价相关的"公允"口径均不含增值税）。
- 填公允法时，每个商品行的公允价值都要按不含税口径填，与含税/不含税成本字段的"税"区分开。
- **成本法下公允价值可填 0**（分摊是成本时公允价值是没必要字段）。

### 业务语义：推广 & ROI（重要，先理解再填）

> ⚠️ **红线（实测会出错）：不做推广，就【不要填推广名称】！** 填了推广名称 = 告诉站点"我要做推广"，后续会走推广计算逻辑；如果没配套填 ROI 等（或填错），**保存/流程会出错**。要做推广 → 名称+ROI 一起填；不做 → 名称留空（整段不存，按无推广处理）。**绝不能只填个名称放着。**

> HTML 第 131 行 ROI 输入框 placeholder 原文：`ROI=GMV/推广成本`。

**推广模块的使用边界**：
- **必须有推广名称才能启用推广**：`advertising_name` 为空时整段不存（`getParams_Advertising` 返回 null），后续流程（报告/敏感性分析）按"无推广"处理。
- **推广 = 广告模式**（京东快车、直通车、引力魔方等广告投放）。**直播、淘宝客等渠道通常不用推广模块**——因为推广有一个非常关键的指标 ROI，只有广告投放才有明确的 GMV/花费关系。

**本工具里所有 ROI 的定义（极其重要，与真实 ROI 完全不同）**：
- **ROI = GMV / 推广成本（广告费用）**，全站统一——参数页的 ROI、报告页、6 个敏感性分析图里出现的 ROI，**全都是这个逻辑**，绝对不是真实 ROI（真实 ROI 一般是 利润/投入 之类）。
- **⚠ ROI 是输入参数，不是输出指标**：参数页填的 ROI 是"每 1 元推广费期望带来多少 GMV"的**预期值**，站点用它反推推广成本（推广成本 = GMV / ROI）；**ROI 数值不受退款率影响**（用户填多少就是多少）。**受退款率+回收率影响的是报告输出的「广告成本」**（广告费用_有效成本 = 退款后广告费 + 广告退款损失，见 `references/qa.md` Q1）。
- **⚠ 不可与电商平台 ROI 直接对比**：平台（淘宝/京东/拼多多/抖音）后台的 ROI 是**统计口径**，与本工具的输入 ROI 不是一回事；别拿输入 ROI 和平台统计 ROI 直接比（详见 `references/qa.md` Q1/Q2）。
- **推广成本 ≠ 报告里的广告成本**：这里的推广成本是**计算之前的**广告推广花费（用 GMV 和 ROI 反推：推广成本 = GMV / ROI），是模型的输入参数；报告页里的"广告成本"是推演后按实际结果算出来的（含退款损失），两者含义不同、数值不同。
- 所以填 ROI 时心里换算的是：**每花 1 元推广费能带来多少 GMV**（ROI=3 即 1 元换 3 元 GMV）。

**推广回报率（工具更侧重的指标）**：
- 相比真实 ROI，本工具更看重**推广回报率**——按**实际推广成本**和**推演出来的利润**计算（推广回报率 = 推演利润 / 实际推广成本）。
- 这比 ROI 价值更高：ROI 只反映 GMV 对推广费的关系，推广回报率反映的是**钱花出去最终赚了多少**。
- **涉及 ROI 或推广时，主动引导用户关注推广回报率**（报告页指标卡、ROI 图图例都有这个指标），并提醒 ROI 陷阱（自然成交变推广成交=无效推广，见 `references/qa.md` Q4）。

**推广模块字段与模型对应**（存 `modelPlanParamsAdvertising`，单对象或 null）：
| 页面字段 | 选择器 | 模型字段 | 说明 |
|---------|--------|---------|------|
| 推广名称 | `#advertising_name` | `name` | **不做推广必须留空**（填了会出错）；要做推广才填（名称+ROI 一起） |
| ROI | `#advertising_roi` | `roi` | **= GMV/推广成本**，>0 |
| 推广税率 | `#advertising_rate` | `inputRate` | 页面 %，存 0-1 |
| 售前/售中/售后回收率 | `#advertising_refund_bef_rec` 等 | `refundBefRec/IngRec/AftRec` | 页面 %，存 0-1；推广自身的退款回收 |

### 业务语义：退款 vs 回收率（重要，先理解再填）

> 页面官方说明（HTML 第 518 行「退款回收率设置」）：**回收率 = 发生退款时，退款的损失能回来多少**。
> 例：商品成本 1000 元，回收率 80% → 800 元回收、200 元损失（损失可以是丢失、损坏、折价回收等任何形式）。

**回收率是"整体逻辑回收率"，不是单笔订单的**（重要）：
- 它描述的是**一批退款订单整体的平均水平**，不是某一单的具体情况。比如"退款 100 单，整体回收率 80%"＝ 这 100 单作为一个整体，平均能回收其货值/成本的 80%，损失 20%。
- 实际单笔可能千差万别（有的单全损 0%、有的单完好 100%），但模型只关心**整体比例**：填 80% 即"这一批退款整体回来 8 成"。
- **三个阶段各有一个整体回收率**：售前退款的那批、售中退款的那批、售后退款的那批，各自按整体回收率计损。填值时按"这个阶段整体大概能回来多少"来估，而不是纠结某一单。

**「目标」模块的三个退款（售前/售中/售后）是方案级总退款率**，影响范围有明确边界（已与 HTML 各表头核对）：

| 模块 | 退款率来源 | 回收率 | 说明 |
|------|-----------|--------|------|
| 商品信息（Goods） | 用**目标模块**的退款 | ✅ 每行售前/售中/售后回收 | 目标退款 × 该商品回收率 = 该商品的退款损失 |
| 赠品信息（Gift） | 用**目标模块**的退款 | ✅ 每行售前/售中/售后回收 | 同上 |
| 每单支出（ExpensePerOrder） | 用**目标模块**的退款 | ✅ 每行售前/售中/售后回收 | 同上 |
| 部分订单支出（ExpenseMNPerOrder） | **单独填写**（每行有售前/售中/售后退款列） | ✅ 每行售前/售中/售后回收 | 退款率独立，不依赖目标模块 |
| 固定支出（ExpenseFixed） | **无退款这回事** | **无回收率列** | 固定支出不随订单/退款变化 |
| 推广（Advertising） | 单独填广告退款回收率 | 3 个回收率 | 广告自身的回收，见 §各模型字段 |

**⚠ 单量过小 → 退款取整反超 → 有效单量变负（2026-08-22 实测确认，务必避免）**：
- 本站退款**模拟真实退款**：不存在"退 0.1 个订单"，退款单量会**向上取整（ceil）**（源码 `SimulationCore`：订单数量_退款后 = 单量 × (1−总退款率)，`ROUND_DOWN`；各阶段损失取整后做差额补偿）。
- 当目标单量很小（1 / 2 / 3）时，取整误差被放大：例 单量 3、总退款 8% → 退款单量取整后 ≈ 3 → **有效单量 0 甚至负数**，报告出现荒谬值（有效单量 -2 / 销售额 -279 / 利润率 -Infinity 等）。
- **目标单量建议 ≥10（最好 10 的倍数）**：让退款取整误差占比足够小，报告数字才可信。读报告遇到明显荒谬负值/Infinity，先查目标单量是否过小。
- 这也解释了历史"全 3 数（3/33/333）"现象的本质：**不是卡死，而是小单量 + 退款取整导致数字错乱**（2026-08-22 实测：单量 1/2/3 报告能打开但数字错，单量 10 正常）。

**记忆要点**：
- **目标模块的退款影响**：商品 / 赠品 / 每单支出（这三个模块自己没有退款率，只有回收率）。
- **部分订单支出的退款率单独填**：它有自己的售前/售中/售后退款列（因为它只作用于"部分订单"，比例含义与全局退款不同）。
- **固定支出没有退款**：表头无退款、无回收，任何阶段都不涉及。
- **回收率是"回来多少"且是整体逻辑**：80% = 损失 20%；数值越大损失越小；按"这一批退款整体回来几成"估，不是按单笔。

## 5. 源码级坑（务必注意）

1. **参数页强依赖 URL 三参数**：`workspaceId` / `groupId` / `planId` 缺一不可，否则页面直接隐藏（不是报错，是整页替换成"方案不存在"）。脚本导航必须先拿全三个 ID。
2. **百分比一律存 0-1 小数**：退款比例、税率、回收率、订单比例，页面输入是 %（如 13），存储是 0.13。读写脚本千万别把 13 当 13% 直接存——读时 `.value` 就是 0-1，写时要先除以 100（或按页面输入格式传）。
3. **数值全是 `{value, options}` 包装对象**：直接读 IDB 时看到 `salePrice: {value:"99", options:{...}}` 是正常的，取 `.value`（字符串）再 `Number()` 转换。**不要**把整个对象当值传给 UI 或报告逻辑。
4. **广告 name 为空 = 整条不存**：`getParams_Advertising` 在 name 空时返回 null，`savePlanParams` 会把整个 `modelPlanParamsAdvertising` 存为 null。读脚本要容忍 null。
5. **⚠ 固定支出的"基于"（base）选项与其他两类不同**：PerOrder / MN 的 base 是 `["-", "售价"]`（per 类型选"售价"）；**Fixed 的 base 是 `["-", "付款金额", "销售金额", "收入", "利润"]`——没有"售价"，per 类型选"利润"**（脚本已按此处理：`--expense-fixed` 第 5 项可指定基于，默认"利润"）。
6. **商品/赠品/费用是数组**：表格可多行。读脚本 `Array.isArray()` 判断；个别历史数据可能是单对象（parse 兼容），也要处理。
7. **`expenseFixed` 的 valueType 默认**：Model 里 `valueType` 缺省时按 `'num'`（金额）处理；UI 上有 `cost_type_money` / `cost_type_percent` 单选按钮对应 num/per。
8. **保存成功 toast 是 `方案参数保存成功！`**：与方案组（`方案组创建成功`）、方案（`方案更新成功`，误导文案）都不同，别混。

## 6. 红线

- **写参数走参数页 UI**（复用站点的 8 类校验：正数/整数/0-100%/总和≤1），**不要**直接 `put` 进 planParams store 绕过校验。
- **百分比换算**：UI 输入 % → 存储 0-1；读脚本输出时可按需 ×100 展示。方向搞反会让报告数据全错。
- **不做推广就绝对不要填推广名称**——填了会出错（推广逻辑被激活但参数不完整）。要推广 → 名称+ROI 一起填；不推广 → 名称留空（见 §业务语义：推广 & ROI）。
- **赠品被强制按「销售费用」处理时，必须先提醒税法规定 + 给链接 + 说明偷税漏税后果，再按用户需求执行**（见 §业务语义：赠品）。
- **不要动 `id`**：planParams.id 必须等于方案 id，改了会脱离方案（孤儿）。
- 删除方案前先 `plan_meta_ops.js params` 评估孤儿；删方案后参数不会自动删。
- 浏览器常驻模式，收尾用 `--close`；Edge Canary 被手动打开时先关掉或用调试端口启动。
